# Mindtraveller — Initial Requirements

**Version:** 0.1  
**Status:** Initial Draft  
**Project Type:** AI-Powered Text-Based RPG

## 1. Project Overview

Mindtraveller is an AI-powered text-based RPG application designed to recreate the nostalgic experience of early computer role-playing games.

Unlike traditional text-based RPGs, Mindtraveller uses modern Large Language Models (LLMs) to dynamically generate stories, events, and player choices.

The player experiences an interactive adventure where their decisions influence how the story unfolds.

The initial version will focus on medieval fantasy settings, simple character creation, AI-generated storytelling, and a retro-inspired graphical interface.

## 2. User Interface

The application should follow a retro desktop design inspired by Windows 95/98 and classic computer RPGs.

The provided reference image (`reference_prototype_1.png`) should be used as the primary visual reference.

### 2.1 Main Layout

The interface should contain:

- **Sidebar:** Application logo and navigation buttons.
- **Story Area:** A scrollable text panel displaying the AI-generated narrative.
- **Decision Area:** A panel displaying the available player choices.
- **Status Bar:** A bottom section displaying basic application information.

### 2.2 Navigation

The sidebar should contain the following options:

| Option | Description |
|---|---|
| New Story | Starts the character creation and story initialization process. |
| Rules | Displays game rules and character information. |
| Settings | Configures the LLM connection. |
| Quit | Closes the application. |

## 3. Story Creation

When the player selects **New Story**, the application should start a guided story creation process.

### 3.1 Story Theme

The player must select one of the following medieval story themes:

- **Horror:** Dark medieval stories involving mystery, supernatural threats, and frightening events.
- **Romance:** Medieval adventures emphasizing relationships, emotions, and character interactions.
- **High Fantasy:** Traditional fantasy adventures involving magic, mythical creatures, and epic quests.

The selected theme should influence the narrative generated by the LLM.

### 3.2 Character Attributes

After selecting the story theme, the player must distribute attribute points according to the game's character system (check in `probabilitySystem.md`).

The available attributes, their effects, and their allowed ranges must follow the rules defined in the separate character rules specification.

The player must choose one of two attribute allocation methods:

**Method A — Balanced Distribution**

- Distribute a total of 5 positive attribute points.
- Distribute a total of 2 negative attribute points.
- All attributes must remain within their allowed ranges.

**Method B — Simplified Distribution**

- Distribute a total of 3 positive attribute points.
- No negative attribute points are required.
- All attributes must remain within their allowed ranges.

The application must validate the distribution before allowing the player to continue.

### 3.3 Character Identity

After attribute allocation, the player must define:

- Character name.
- Character gender.

The selected identity and attributes should be included in the context provided to the LLM.

### 3.4 Story Initialization

Once character creation is complete:

1. The application sends the selected theme, character information, and relevant game rules to the configured LLM.
2. The LLM creates an original story premise.
3. The LLM generates the opening narrative.
4. The LLM provides the first set of player choices.

The initial story should be consistent with the selected theme and character characteristics.

## 4. Storytelling and Player Interaction

### 4.1 Narrative Generation

The LLM is responsible for generating the story dynamically.

By default:

- Each narrative segment should contain approximately 2–3 paragraphs.
- The number of paragraphs must be internally configurable.
- The narrative should maintain continuity with previous events.
- Character attributes and established story facts should influence events when relevant.

### 4.2 Player Choices

At the end of each narrative segment, the LLM should generate 3–4 possible actions.

The number of choices should be internally configurable.

Each choice should:

- Represent a meaningful action available to the player.
- Be consistent with the current situation.
- Potentially influence subsequent events.

### 4.3 Story Progression

The main gameplay loop should follow this sequence:

1. The LLM generates a narrative segment.
2. The application displays the generated text.
3. The application displays the available choices.
4. The player selects one choice.
5. The selected action is added to the story context.
6. The LLM generates the next narrative segment and choices.
7. The process repeats.

The application should prevent multiple simultaneous submissions while waiting for the LLM response.

## 5. Context Management

Mindtraveller must support long-running adventures without depending on the entire conversation history being included in every LLM request.

### 5.1 Hierarchical Summarization

The application should implement **Hierarchical Summarization** to manage story context.

The story context should be organized into three levels:

**Level 1 — Recent Events**

Contains the most recent narrative segments and player decisions.

This information should be preserved in sufficient detail to maintain immediate story continuity.

**Level 2 — Chapter Summaries**

The adventure should be divided into chapters.

- Each chapter contains a configurable number of narrative segments.
- When a chapter reaches its configured limit, the system generates a summary.
- Chapter summaries should preserve important events, decisions, characters, and consequences.

**Level 3 — Global Story Summary**

A higher-level summary should represent the overall adventure.

It should preserve:

- Major story developments.
- Important characters and relationships.
- Significant player decisions.
- Unresolved conflicts and objectives.
- Relevant world information.

The global summary should be updated as the adventure progresses.

### 5.2 Context Construction

When requesting a new narrative segment, the application should construct the LLM context using:

- System instructions and game rules (`probabilitySystem.md`).
- Character information and attributes.
- Selected story theme.
- Global story summary.
- Relevant chapter summaries.
- Recent narrative events.
- The player's latest decision.

The objective is to reduce token consumption while maintaining narrative consistency.

### 5.3 Configurability

The following parameters should be configurable internally:

- Number of narrative segments per chapter.
- Number of recent narrative segments retained in context.
- Maximum context size or token budget.
- Summarization thresholds.

These parameters do not need to be exposed in the user interface for the initial version.

## 6. LLM Integration

The application must support two LLM connection methods.

### 6.1 Ollama — Local Connection

The player should be able to connect to a locally running Ollama instance.

The configuration should support:

- Ollama server address.
- Selection of an available local model.

The application should use the selected local model for narrative generation and context summarization.

### 6.2 OpenAI — External Connection

The player should be able to connect to OpenAI using an API key.

The configuration should support:

- OpenAI API key.
- Selection of an available or supported model.

The application should use the configured OpenAI model for narrative generation and context summarization.

### 6.3 Provider Selection

The Settings screen should allow the player to select the active LLM provider.

The application should use the selected provider for subsequent LLM operations.

The system should provide appropriate error messages when:

- The selected provider is unavailable.
- Authentication fails.
- The configured model cannot be accessed.
- A request fails or times out.

API credentials must not be exposed in logs or story content.

## 7. Rules Screen

The **Rules** section should provide access to the game's rules and current character information.

### 7.1 Game Rules

The player should be able to read:

- General gameplay rules.
- Character attributes and their effects.
- Attribute-based action resolution rules.

The detailed rule definitions should come from the separate game rules specification.

### 7.2 Character Information

The player should be able to view:

- Character name.
- Character gender.
- Current attribute values.

Character information should reflect the active adventure.

## 8. New Story Confirmation

If the player selects **New Story** while an adventure is active, the application must display a confirmation modal.

Example message:

"Are you sure you want to start a new story? Your current adventure will be replaced."

The modal should provide two options:

- **Yes:** Discard the current active adventure and restart the story creation process.
- **No:** Close the modal and return to the current adventure.

The current adventure should remain unchanged until the player confirms.

## 9. Quit Application

When the player selects **Quit**, the application should close.

Any necessary cleanup of active LLM requests or application resources should be handled before termination.

## 10. Initial Version Scope

### Included in v0.1

- Retro-inspired desktop user interface.
- Medieval story theme selection.
- Character creation and attribute distribution.
- AI-generated narratives.
- AI-generated player choices.
- Interactive story progression.
- Hierarchical context summarization.
- Configurable narrative and context parameters.
- Ollama integration.
- OpenAI integration.
- Rules and character information screen.
- New Story confirmation.
- Application exit functionality.

### Out of Scope for v0.1

- Multiplayer gameplay.
- Graphical combat systems.
- Character animations.
- Voice narration.
- Image generation during gameplay.
- Cloud synchronization.
- Multiple simultaneous adventures.
- Advanced inventory and equipment management.
- User accounts and authentication.

## 11. General Design Principles

The initial implementation should follow these principles:

**Simplicity:** Prioritize a functional, enjoyable text-based RPG experience over complex gameplay mechanics.

**Modularity:** Keep the LLM integration, context management, game rules, and user interface logically separated.

**Configurability:** Avoid hardcoding narrative generation and context management parameters.

**Provider Independence:** The storytelling system should not depend on a specific LLM provider.

**Narrative Consistency:** Preserve important story events, player decisions, and character information throughout long adventures.

**Retro Experience:** Maintain the visual identity and simplicity of early desktop RPG applications.
